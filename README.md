# Telegram Business personal assistant

A bot that connects to your personal Telegram account through Telegram Business
("Chatbots") and drafts replies in your name and your style, using facts from `profile.md`.
Replies are generated by the Claude Code CLI (`claude -p`) with your Claude subscription.
An Anthropic API key is never used.

## What it does

- **Preview mode is the default.** With `AUTO_SEND=false`, drafted replies appear only in the
  logs and in `data/previews.jsonl`. Nothing is sent until you set `AUTO_SEND=true`.
- There is no allowlist in the code. **Which chats the bot sees is decided only by Telegram**,
  in *Settings → Telegram Business → Chatbots*.
- It runs on Railway with long polling, so it needs no domain, webhook or open port.

## Behaviour

| Situation | What happens |
|---|---|
| Connection belongs to another account | Ignored, a warning is logged, Claude is not called |
| Which chats are handled | Whatever you selected in Telegram's *Chatbots* setting |
| You write in a chat yourself | Saved to history, never answered. The bot stays silent there for `OWNER_TAKEOVER_MINUTES` |
| Message from a bot, or the bot's own reply | Ignored |
| Same message delivered twice | Handled once, even across restarts |
| Service message (pin, title change, ...) | Ignored |
| Media | Described to Claude, e.g. `[voice message]`, `[photo] caption`, `[sticker] 😀` |
| `/pause` | No replies until `/resume`. Survives restarts |
| Subscription usage limit | No retries until the reset time (or `LIMIT_COOLDOWN_MINUTES`). Survives restarts. In auto-send mode you get one message |
| Timeout or login error | Logged, nothing goes to the chat. In auto-send mode you get at most one message per 10 minutes |
| Claude answers `[SKIP]` | Nothing is shown or sent |
| Just before an auto-send | Pause, limit and takeover are rechecked, and the connection is fetched fresh from Telegram (owner, enabled, `can_reply`). If any check fails, nothing is sent |

Owner commands, in a private chat with the bot:

| Command | Effect |
|---|---|
| `/start` | Setup guide and current state, in Uzbek |
| `/pause` | Stop replying |
| `/resume` | Clear the pause, limit and takeover timers |
| `/status` | Mode, state, limit and number of chats in history |

Anyone else who sends `/start` gets a short note in Uzbek saying this is a personal bot.
Claude is not called, and nothing about the owner is revealed. Other messages are ignored.

## How Claude is called

Each reply is one process, started without a shell:

```
claude -p --safe-mode --settings <json> --tools "" --strict-mcp-config --setting-sources ""
  --disable-slash-commands --no-session-persistence --system-prompt-file <temp file>
  --output-format json --effort <level>
```

- The conversation is passed **only through stdin**. The system prompt, which includes your
  profile, is in a private temporary file that is deleted afterwards. Neither appears in `ps`.
- `--settings` turns off hooks and every builtin plugin. The CLI has no tools, MCP servers or
  skills, and it runs in an empty directory, `data/claude-run`.
- **`--bare` is not used** because it ignores the OAuth login, so the subscription would not work.
- The child environment loses everything starting with `ANTHROPIC_`, the bot token, any inherited
  Claude token, the Bedrock/Vertex/Foundry switches, and `CLAUDE_CODE_SIMPLE`.
- The token from `claude setup-token` (`sk-ant-oat...`) is given only to the child process
  through its environment. An API key (`sk-ant-api...`) is refused at startup. The token is
  replaced by `[REDACTED]` in CLI output before it is parsed.
- `python bot.py --check-claude` proves all of this on the real CLI. It exits with code 1 if
  tools, MCP servers, plugins or skills are present, or if an API key is in use.

## Deploy to Railway

1. On a computer with a browser, run `claude setup-token` and keep the `sk-ant-oat...` token.
2. In @BotFather, run `/newbot`, then turn on *Bot Settings → Business Mode*. Get your numeric
   ID from @userinfobot.
3. Create a **private** GitHub repository and push the code. `profile.md` goes into the Docker
   image, which is why the repository must be private.
4. In Railway: New Project → GitHub Repository → your repository.
5. Open Service → Variables → Raw Editor and set `TELEGRAM_BOT_TOKEN`, `OWNER_ID`,
   `CLAUDE_CODE_OAUTH_TOKEN` and `AUTO_SEND=false`. Optional: `CLAUDE_MODEL`, `CLAUDE_EFFORT`
   and the other settings in `.env.example`. `CLAUDE_BIN`, `DATA_DIR` and `PROFILE_PATH` are
   not needed.
6. Add a Volume: right-click the canvas (or press Cmd+K) → Volume → pick the service → set the
   mount path to exactly `/app/data` → Deploy. Without a Volume, history, pause and limit state
   are lost on every deploy.
7. Check Logs for `Bot @... is running`, `Mode: PREVIEW` and
   `Claude auth: subscription token from environment variables`. Red text in Railway only means
   stderr, not an error.
8. Send `/start` to the bot. Then in Telegram open *Settings → Telegram Business → Chatbots*
   (Telegram Premium is required), enter the bot's username, select the chats, and allow it to
   reply. The log should show `Business connection ...: user=<id> enabled=True`.
9. When someone writes to you, a `PREVIEW, not sent` block appears in the logs. If the drafts
   look right, set `AUTO_SEND=true`.

Notes:

- Run the bot in one place only. Two pollers with the same token interfere with each other, so
  do not run `python bot.py` locally while Railway is running.
- Every push redeploys. Changing `profile.md` also needs a commit and push.
- If the Claude token expires or leaks, run `claude setup-token` again and update the Railway
  Variable. If the bot token leaks, use `/revoke` in @BotFather.

## Local development

```bash
python -m venv .venv
.venv/bin/pip install -r requirements-dev.txt     # Windows: .venv\Scripts\pip
cp .env.example .env && chmod 600 .env
python bot.py --check-claude
python bot.py --try "Salom, qalesan?"
```

Paste the token into `.env` with a text editor. If `CLAUDE_CODE_OAUTH_TOKEN` is left empty, this
machine's `claude` login is used.

Windows works for development. POSIX file modes do not apply there, so permission checks are
skipped, and timeouts end the process tree with `taskkill` instead of a process group.

## Commands

| Command | Purpose | Exit codes |
|---|---|---|
| `python bot.py` | Run the bot using `.env` | 0, 2 on bad settings or a rejected bot token |
| `python bot.py --settings-from-env` | Run in a container using environment variables | same |
| `python bot.py --check-claude` | Check the real CLI session, no Telegram needed | 0, 1 on failure, 2 on bad settings |
| `python bot.py --try "text"` | Draft a reply to a made-up message, no Telegram needed | 0, 1 on failure, 2 on bad settings |

`--check-claude` and `--try` can be combined with `--settings-from-env`.

## Tests

```bash
.venv/bin/python -m pytest
```

All tests run without network access. The CLI tests use a fake `claude` executable.
